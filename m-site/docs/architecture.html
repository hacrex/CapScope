Architecture

CapScope is a single Go binary with no frontend build step — the UI is an embedded HTML file. It runs as one container next to the containers it watches.

Docker Engine → CapScope (one Go binary) → SQLite (one file)
    │
    ├─ collector: follows logs + stats per container
    ├─ hub: SSE fan-out to the browser
    ├─ store: WAL mode, batched inserts, retention
    └─ api: REST + SSE + embedded single-page UI

Overview

CapScope watches your Docker daemon, stores logs and CPU/memory samples in SQLite, and keeps a crash snapshot every time a container exits non-zero or is OOM killed. When a container is redeployed and disappears, its logs and memory trend are still searchable — unlike live-only log viewers where the evidence dies with the container.

Components

Collector

Discovers running containers at startup and on Docker start/die events, reconciles every 30s. Follows stdout/stderr per container and samples CPU, memory, network, block I/O, and pids at a configurable interval (default 10s).

Hub

SSE fan-out to the browser. The live log view uses Server-Sent Events so the UI streams new log lines as they arrive, with pause/follow and load-older support.

Store

SQLite in WAL mode with synchronous=NORMAL and batched inserts (~156k rows/sec measured upper bound). Enforces age and size retention, dropping oldest logs first when the MAX_DB_MB cap is reached.

API

REST endpoints for containers, logs, metrics, crash snapshots, access logs, SQL queries, alerts, and deploys. Basic auth by default; read-only Docker access.

Data flow

  1. Discover — containers are discovered at startup and reconciled every 30 seconds.
  2. Collect — the collector follows each container's logs and stats, redacting secrets before storage.
  3. Persist — logs, metrics, and metadata are written to SQLite in WAL mode.
  4. Snapshot — on container die (OOM or non-zero exit), a crash snapshot is written with exit code, last log lines, memory trend, and a rule-based summary.
  5. Serve — the API serves the UI and SSE streams; the browser renders logs, charts, and crash details.

Secrets (JWTs, bearer tokens, passwords, keys, etc.) are redacted before storage. Environment variables and labels are never stored.

Security

  • Basic auth required by default; server refuses to start without a password unless you explicitly opt out (ALLOW_NO_AUTH=true).
  • Read-only use of the Docker API; works through a socket proxy over TCP.
  • Docker socket access is root equivalent — use auth, HTTPS, and preferably a read-only socket proxy in production.
  • Client IPs are anonymized by default in stored access logs (ANON_IPS=false to disable).
