Audit log

Append-only admin audit trail for security-sensitive actions. Every login, SQL query, alert rule save, deploy, user management action and incident state change is recorded — filterable by actor and action.

API

GET /api/audit List audit entries, newest first; filter by ?actor=, ?action= and ?limit= (admin only)

Audit writes are fail-closed: a database error is logged but never blocks the underlying action. Audit entries are written for login, logout, SQL queries, alert rule saves, deploy creates, user management (create/role/apps/delete) and incident state changes.

Audit entry fields

FieldMeaning
idAuto-incrementing entry id
tsWhen the action occurred (unix ms)
actorWho performed the action — user name, user id, proxy or anonymous
actionWhat was done: login, logout, sql, alert_rule, deploy, user_mgmt or incident
resourceThe resource acted on — e.g. /api/sql, an app name, a user id, an incident id
targetAdditional target context (e.g. rule count, version, role)
metaJSON blob of extra context (e.g. channel names, apps assigned)

Actions tracked

ActionTriggered by
loginSuccessful POST /api/login (includes auth provider)
logoutPOST /api/logout
sqlGET /api/sql (includes the query text truncated to 200 chars and limit)
alert_rulePOST /api/alerts/rules (includes rule count)
deployPOST /api/deploys (includes app, version and note)
user_mgmtCreate / role change / app assignment / delete via the users API
incidentPOST /api/incidents/{id}/state (includes the new state)

Example entry

JSON 
{
  "id": 42,
  "ts": 1793158659437,
  "actor": "admin",
  "action": "sql",
  "resource": "SELECT app, level, count(*) FROM logs WHERE ts > ... GROUP BY app, level",
  "target": "limit=1000",
  "meta": {}
}
Retention: Audit entries share the database retention and size caps — they are subject to the same MAX_DB_MB and LOG_RETENTION policies as other data.
